# forgejo-pr-llm

Консольная утилита: выгружает открытые Pull Request из Forgejo в JSON-снимки и
прогоняет каждый снимок через LLM с OpenAI-совместимым API (локальной или внешней).

```
Forgejo API ──► <N>_<sha>.json ──► LLM (chat/completions) ──► answer_<N>_<sha>.txt
```

С флагами `--post-review` или `--post-draft-review` замечания LLM дополнительно размещаются в PR как inline-комментарии одного review (см. раздел «Размещение замечаний в PR»).

## Установка

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# для запуска тестов
pip install -r requirements-dev.txt
```

Поддерживаются Python 3.10–3.13 (эти версии проверяет CI). Docker-образ собирается на базе `python:3.12-slim`.

### Docker

```bash
docker build -t forgejo-pr-llm .
docker run --rm -e FORGEJO_TOKEN -v "$PWD:/data" forgejo-pr-llm \
    https://forgejo.example.com/owner/repo \
    --llm-url http://host.docker.internal:11434/v1/chat/completions \
    --model qwen2.5-coder:14b \
    --prompt-file prompt.txt \
    --output-dir ./out
```

Контейнер работает от пользователя `appuser` (uid 1000), рабочий каталог — `/data`. Смонтированный каталог должен быть доступен этому пользователю на запись. Внутри контейнера `localhost` — это сам контейнер, поэтому для LLM на хосте укажите `host.docker.internal` (Docker Desktop) или запускайте контейнер с `--network host` (Linux).

## Быстрый старт

```bash
export FORGEJO_TOKEN=your_token_here

python3 forgejo_pr_llm.py https://forgejo.example.com/owner/repo \
    --llm-url http://localhost:11434/v1/chat/completions \
    --model qwen2.5-coder:14b \
    --prompt-file prompt.txt \
    --output-dir ./out
```

Файл `prompt.txt` нужно создать самостоятельно (пример — в разделе «Пример промпта»).

Токен можно передать и через `--token`; вариант с переменной окружения
предпочтительнее — значение не попадает в `ps` и историю shell.

### Токен и права

Создайте токен: **Settings → Applications → Generate New Token**.
Нужны scope:

- `read:repository` — сам PR, файлы, коммиты, диффы;
- `read:issue` — комментарии и timeline (issue-API);
- `write:repository` — только для `--post-review` / `--post-draft-review`: создание review и inline-комментариев.

При ошибке `403` программа подскажет, каких прав не хватает.

## Параметры

| Параметр | Обяз. | По умолчанию | Описание |
|---|---|---|---|
| `REPO_URL` | да | — | Полный URL: `https://host/owner/repo`. Поддерживаются подпути (`https://host/git/owner/repo`), суффикс `.git` и хвосты (`…/src/branch/main`) |
| `--token` | да* | `$FORGEJO_TOKEN` | Токен доступа |
| `--llm-url` | да | — | **Полный** endpoint, напр. `http://localhost:11434/v1/chat/completions` |
| `--model` | да | — | Имя модели на endpoint |
| `--prompt-file` | да | — | Файл с текстом промпта |
| `--label` | нет | все | Фильтр по меткам: список через запятую или повторный флаг; `-метка` исключает |
| `--assignee` | нет | все | Только PR с этим assignee (логин) |
| `--title-contains` | нет | все | Только PR, в заголовке которых есть подстрока (без учёта регистра) |
| `--openai-api-token` | нет | `$OPENAI_API_TOKEN` | Bearer-токен для LLM endpoint |
| `--output-dir` | нет | `.` | Каталог результатов |
| `--llm-timeout` | нет | `900` | Ожидание ответа LLM, секунды |
| `--llm-retries` | нет | `3` | Число попыток запроса к LLM, включая первую |
| `--http-timeout` | нет | `60` | Таймаут запросов к Forgejo, секунды |
| `--http-retries` | нет | `3` | Число попыток GET-запросов к Forgejo (POST не повторяется) |
| `--page-size` | нет | `50` | Размер страницы API (1–50, ограничение Forgejo) |
| `--max-file-bytes` | нет | `524288` | Лимит размера файла (512 КБ): файлы крупнее не выгружаются, `skipped_reason` = `too_large` |
| `--max-prompt-bytes` | нет | `1048576` | Порог предупреждения о размере запроса к LLM |
| `--no-stream` | нет | выкл. | Не печатать ответ LLM по мере генерации (запрос всё равно идёт со `stream: true`) |
| `--refresh` | нет | выкл. | Перекачать JSON, даже если файл есть |
| `--force-llm` | нет | выкл. | Повторить запрос к LLM, даже если ответ есть |
| `--dry-run` | нет | выкл. | Показать список PR, ничего не записывать |
| `--post-draft-review` | нет | выкл. | После проверки разместить замечания LLM в PR **черновиком** review (виден только владельцу токена) |
| `--post-review` | нет | выкл. | То же, но сразу **опубликованным** review (событие `COMMENT`). Взаимоисключается с `--post-draft-review` |
| `--force-review` | нет | выкл. | Разместить review повторно, даже если для этого PR и коммита он уже размещался. Требует `--post-review` или `--post-draft-review` |
| `--comment-filter` | нет | все | Только комментарии и inline-комментарии указанных логинов: список через запятую или повторный флаг; `-логин` исключает |
| `--light-pr` | нет | выкл. | Облегчённый снимок: только файлы с патчами и неразрешённые inline-комментарии (см. «Облегчённый режим») |
| `--version` | нет | — | Показать версию утилиты и выйти |

\* Токен обязателен: задайте `--token` или переменную `FORGEJO_TOKEN`.

`--label` и `--assignee` работают по логике **И**: если заданы оба, PR должен
совпадать по обоим условиям. Совпадение меток и логинов — регистронезависимое. `--title-contains` добавляет к ним ещё одно условие (**И**): подстрока ищется в заголовке PR без учёта регистра.

### Фильтр по меткам

Меток можно задать сколько угодно — через запятую в одном значении или
повторив флаг. Метка без префикса **обязательна**, с префиксом `-` — **запрещена**:

```bash
# нужны обе метки bug и needs-review, и не должно быть wip
--label bug,needs-review,-wip

# то же самое отдельными флагами
--label bug --label needs-review --label -wip
```

Правила:

- все обязательные метки должны присутствовать одновременно (**И**);
- ни одной запрещённой метки быть не должно;
- регистр не важен (`Bug` == `bug`);
- метку, начинающуюся с дефиса, задавайте с префиксом `+` (`--label +-weird`) или в одинарных кавычках (`--label '\-weird'`): без кавычек shell убирает `\`, и `\-weird` превращается в `-weird`, то есть в запрещённую метку;
- метка, заданная и как обязательная, и как запрещённая (`bug,-bug`), —
  ошибка конфигурации (код 2), как и пустое значение `--label`.

Обратите внимание: `--label -wip` работает благодаря нормализации аргументов,
но надёжнее писать `--label=-wip` — так значение не спутается с опцией.

### Токен для LLM

`--openai-api-token` отправляется как `Authorization: Bearer <token>` в запросах
к `--llm-url`. По умолчанию берётся из `$OPENAI_API_TOKEN`. Если токен не задан,
заголовок не отправляется — это годится для локальных серверов без авторизации
(Ollama, LM Studio, vLLM).

Токен Forgejo (`--token`) **никогда** не передаётся в LLM: это отдельные
креденшелы, и они не смешиваются.

## Размещение замечаний в PR

С флагом `--post-draft-review` или `--post-review` после ответа LLM замечания
размещаются в самом PR как inline-комментарии одного review:

| Флаг | Что создаётся |
|---|---|
| `--post-draft-review` | **Черновик** review (`PENDING`): виден только владельцу токена, пока тот не опубликует его в веб-интерфейсе |
| `--post-review` | **Опубликованный** review (событие `COMMENT`), сразу виден автору PR. Ответ модели попадает в PR без проверки человеком |

Флаги взаимоисключающие, нужен токен со scope `write:repository`.

Ответ LLM должен быть JSON-списком без обёртки в markdown-блок:

```json
[
  {"file": "src/main.c", "line": "18", "comment_text": "Текст замечания"}
]
```

- `file` — путь файла в репозитории, как в списке изменённых файлов PR;
- `line` — номер строки в **новой** версии файла (число или строка с числом);
- `comment_text` — текст замечания (Markdown).

Что важно знать:

- Комментарии привязываются к коммиту, который проверяла LLM (`head` на момент
  выгрузки), а не к текущему состоянию PR.
- Записи без `file` / `line` / `comment_text`, с `line < 1` или с файлом, которого нет
  среди изменённых в PR, пропускаются с предупреждением, остальные размещаются.
  Если подходящих замечаний не осталось, review не создаётся, а PR считается
  ошибочным (код возврата `1`). Пустой список `[]` ошибкой не считается.
- Ответ, который не является JSON-списком, — ошибка только для этого PR, остальные
  обрабатываются дальше.
- Для пары PR + коммит review размещается один раз: после успеха пишется
  `review_<N>_<sha>.json` с номером review, и повторный запуск такой PR пропускает
  (в том числе когда ответ LLM уже лежал на диске и модель не вызывалась).
  `--force-review` размещает review ещё раз.
- Если у владельца токена в PR уже есть незавершённый review, размещение
  отклоняется: Forgejo добавил бы замечания в него, а `--post-review` ещё и
  опубликовал бы весь черновик целиком. Опубликуйте или удалите черновик и
  запустите снова. Токен администратора сервера видит и чужие черновики, поэтому
  проверка срабатывает и на них.
- Запрос на создание review не повторяется автоматически: после тайм-аута
  неизвестно, создал ли его сервер, и повтор мог бы продублировать review.
  Перед новым запуском проверьте PR.

## Выходные файлы

```
<N>_<sha>.json           # полный снимок PR
answer_<N>_<sha>.txt     # ответ LLM
review_<N>_<sha>.json    # отметка о размещённом review (только с --post-*): mode, review_id, comments, model, posted_at
```

`sha` — head-коммит PR, поэтому при появлении новых коммитов создаётся новая
пара файлов; старые не удаляются. Существующие файлы не перезаписываются
(если не указан `--refresh` / `--force-llm`), так что прерванный запуск
безопасно продолжается повторным запуском.

### Схема JSON

Ключи верхнего уровня:

| Ключ | Содержимое |
|---|---|
| `schema_version`, `fetched_at`, `generator` | Версия схемы, время выгрузки, версия утилиты |
| `source` | `base_url`, `owner`, `repo`, `history_unavailable` |
| `pr_number`, `head_sha` | Номер PR и последний коммит |
| `counts` | Число коммитов, файлов, комментариев, ревью и событий |
| `pull_request` | Ответ `GET /pulls/{index}` целиком, без переименования полей |
| `commits[]` | Все коммиты PR |
| `files[]` | Файлы: `filename`, `status`, `additions/deletions`, `patch`, `patch_source`, `content` |
| `unified_diff` | Общий дифф PR: поля `text` и `truncated` (fallback-источник патчей) |
| `issue_comments[]` | Обычные комментарии |
| `reviews[]` | Ревью с состоянием (`APPROVED`, `REQUEST_CHANGES`, …) |
| `review_comments[]` | Inline-комментарии к диффу, с `_review_id` |
| `timeline[]` | История событий: комментарии, метки, смена assignee, merge, close. При `source.history_unavailable: true` — синтетическая история только из комментариев, ревью и inline-комментариев (`_synthetic: true`) |
| `fetch_errors[]` | Недоступные эндпоинты (`endpoint`, `status`, `message`); не прерывают обработку PR |

Блок `content` у файла:

```json
{
  "encoding": "utf-8",
  "text": "<полное содержимое на head-sha>",
  "size": 4213,
  "binary": false,
  "truncated": false,
  "skipped_reason": null
}
```

Возможные `skipped_reason`: `deleted_in_pr` (файл удалён), `too_large`
(больше `--max-file-bytes`), `not_found`, `forbidden`, `no_content`,
`bad_base64`, `no_head_sha`. Для бинарных файлов `encoding: "base64"`,
`binary: true`, содержимое в `text` в base64.

Сырые ответы API сохраняются как есть — поля не переименовываются, поэтому
схема совпадает с документацией Forgejo и не теряет данных при обновлении
сервера.

### Облегчённый режим (`--light-pr`)

С флагом `--light-pr` в JSON попадают только: `mode: "light"`, `pull_request` (номер, заголовок, состояние, автор, метки, `head`, `base`), `files[]` (`filename`, `status`, `additions`, `deletions`, `changes`, `patch`, `patch_source`) и неразрешённые inline-комментарии `review_comments[]`. Версия схемы — `1.0-light`. Поля `content`, коммиты, комментарии, ревью и timeline в этом режиме не выгружаются.

## Как работает

1. **Авторизация** — `Authorization: token <TOKEN>`.
2. **Список PR** — `GET /repos/{o}/{r}/pulls?state=open`, страницы размером `--page-size` (по умолчанию 50).
   Фильтры применяются после загрузки: `--label` можно было бы отдать серверу,
   но `assignee` в списке PR не фильтруется, а отрицания меток серверный API
   не поддерживает вовсе. Поэтому все условия проверяются локально — так
   поведение одинаково на всех версиях Forgejo.
3. **Сборка снимка** — детали PR, коммиты, файлы, комментарии, ревью,
   inline-комментарии, timeline, полное содержимое каждого файла на `head_sha`.
4. **LLM** — `POST` на `--llm-url` со `stream: true`. Промпт из `--prompt-file`
   идёт как `system`, JSON снимка — как `user`. Ответ печатается в консоль по
   мере генерации, ожидание ограничено `--llm-timeout`.
5. **Запись** — ответ сохраняется атомарно (`.tmp` + `os.replace`), после
   успешного завершения.
6. **Публикация (по флагу)** — замечания из ответа LLM уходят в PR одним
   `POST /repos/{o}/{r}/pulls/{n}/reviews`.

### Устойчивость

- Ошибка одного эндпоинта попадает в `fetch_errors[]` и не прерывает PR.
- GET-запросы к Forgejo повторяются при сетевых сбоях и ответах 408, 425, 429, 500, 502, 503, 504: до `--http-retries` попыток с паузами 2, 4, 8… секунд (не более 30). `Retry-After` учитывается (не более 60 с). POST-запрос на создание review не повторяется.
- Запрос к LLM повторяется при таймауте, сетевой ошибке, ответах 408, 425, 429, 500, 502, 503, 504 и пустом ответе, пока не исчерпаны `--llm-retries` попыток.
- Если сервер отвергает `stream: true` (HTTP 400, 404, 405, 422, 501) или повторы в режиме стриминга исчерпаны, запрос выполняется в обычном режиме с теми же `--llm-retries` попытками.
- Если эндпоинта `timeline` нет (старые версии Forgejo), история собирается синтетически из комментариев и ревью, в JSON ставится `source.history_unavailable: true`.
- `Ctrl+C` не портит файлы: пишутся только завершённые артефакты.

### Особенности, о которых стоит знать

- **Fork-PR.** Содержимое файлов сначала запрашивается из head-репозитория (там лежат коммиты PR), затем — из base-репозитория.
- **Обрезанные патчи.** Некоторые крупные файлы Forgejo отдаёт без `patch`.
  Тогда фрагмент берётся из общего диффа (`patch_source: "unified_diff"`).
- **Размер выгрузки.** Полное содержимое всех файлов — доминирующий фактор объёма (легко десятки мегабайт на серию PR). Уменьшайте `--max-file-bytes`, если JSON слишком велик для контекста модели, или используйте `--light-pr`, если содержимое файлов не нужно.
- **Контекст модели.** Если запрос превышает `--max-prompt-bytes`, печатается
  предупреждение с фактическим размером, но запрос всё равно отправляется —
  решение остаётся за вами.
- **Новые комментарии без новых коммитов.** Имя файла привязано к `sha`, поэтому такие изменения не подхватываются автоматически. Используйте `--refresh`, чтобы перекачать JSON, и `--force-llm`, чтобы заново спросить модель.

## Коды возврата

| Код | Значение |
|---|---|
| `0` | Успех (в том числе когда все файлы уже были, нет подходящих PR или репозиторий пуст) |
| `1` | Обработка завершена, но по части PR были ошибки (в том числе не удалось получить список PR) |
| `2` | Ошибка конфигурации: аргументы (включая `--force-review` без `--post-*`), токен, недоступный репозиторий |
| `130` | Прервано с клавиатуры |

## Пример промпта

Промпт — статическая инструкция: данные PR передаются отдельным сообщением (JSON-снимок), поэтому плейсхолдеры не нужны. Пример содержимого `prompt.txt`:

```text
Ты — автоматический ревьюер Pull Request.
Тебе передан JSON-снимок PR. В `files[].patch` находится дифф файла, в `files[].content` — полный текст файла на head-коммите.

Правила:
- комментируй только строки, добавленные или изменённые в PR (строки с префиксом «+» в `patch`);
- сообщай только о реальных проблемах: ошибках, уязвимостях, нарушениях контракта, заметных проблемах читаемости;
- поле `line` — номер строки в НОВОЙ версии файла (считай по заголовкам `@@ -a,b +c,d @@`);
- если замечаний нет, верни пустой массив `[]`.

Ответ — только JSON-массив без пояснений и без обёртки в markdown-блок:
[
  {"file": "путь/к/файлу.py", "line": 42, "comment_text": "Текст замечания"}
]
```

## Тесты

```bash
python3 -m pytest test_forgejo_pr_llm.py -q
```

Тесты работают на моках HTTP (`responses`), реальные Forgejo и LLM не нужны:
проверяются пагинация, ретраи, 401/403, fork-логика, бинарные и большие файлы,
fallback патчей из диффа, синтетический timeline, SSE-стриминг, таймауты,
несовместимость со `stream: true`, а также идемпотентность, фильтры по меткам
(включая отрицания и краевые случаи разбора аргументов) и передача
Bearer-токена только в LLM-запросы.

CI (`.github/workflows/ci.yml`) дополнительно запускает `ruff check` и `ruff format --check`, прогоняет тесты на Python 3.10–3.13 и собирает Docker-образ.

Для ручной проверки есть фейковый сервер, имитирующий Forgejo и LLM. Запускайте его из корня репозитория, а `prompt.txt` создайте по примеру из раздела «Пример промпта»:

```bash
python3 fake_server.py 8765 &
python3 forgejo_pr_llm.py http://127.0.0.1:8765/owner/repo \
    --token testtoken \
    --llm-url http://127.0.0.1:8765/v1/chat/completions \
```

## Ограничения

- Обработка PR последовательная (по одному) — так проще соблюсти лимиты
  локальной модели и нагляднее прогресс.
- Мерж-коммиты в `commits[]` приходят как обычные коммиты API.
- Вложения к комментариям (attachments) не выгружаются.
- Дифф PR ограничен 8 МБ (см. `unified_diff.truncated`), содержимое файла — `--max-file-bytes`.
